How Freefall was built

Freefall turns NASA's microgravity fire experiments into something you can run yourself. Real test results from the Space Station feed a small physics model; the model drives a 3D flame; a guide answers questions; and the station view shows where each result matters.

The same idea as PhET, with real data underneath

PhET simulations from the University of Colorado are the model we followed for how a science simulation should feel: open it, play, and the idea shows itself. Freefall keeps that feel and adds two things PhET does not need: real measurements from orbit, and a place where the result is put to use.

How the guide stays honest

The guide can use ChatGPT, but it is never the source of a number. ChatGPT is told the current settings and what the model predicts, and it replies with words plus an instruction such as "plot burn rate against oxygen". Freefall then computes that curve from its own model and draws it. If no key is set, a built-in guide answers the common questions the same way.

What is inside

Twenty experiments run on five engines. Experiments that flew on the same kind of hardware share an engine, so a fix or a new control reaches all of them at once.

Around the engines sit four shared parts: the stage (3D view, glow, labels), the flame renderer (it adds up light along each line of sight through the flame), the shell (title, dock of tabs, settings) and the guide (answers, sketches, steps). The station view is the team's own Freefall Fire Console, joined to the labs by a small bridge that knows where each experiment matters on the ISS.

How it was programmed

No build step. The site is plain HTML, CSS and JavaScript modules, with Three.js and the fonts kept in the project. It runs from any folder a web server can read, which is why it can be hosted as static files.

Three small files per experiment. model.js is pure arithmetic: plan(settings) works out the whole burn and at(plan, time) gives the state at one moment. It draws nothing, so it can be tested without a browser. scene.js builds the hardware and the flame from that state. spec.js lists the controls, readings and words. One shared builder turns a spec into a whole lab page.

Real data first. A Python script reads the NASA tables the team collected and writes two small data files: the tests themselves, and the constants fitted to them. The models read those constants, and every lab can replay a logged test next to the model's prediction.

The flame is computed, not painted. A short shader gives the light emitted and absorbed at each point around the fuel. The renderer steps along each line of sight and adds it up, so a thin flame sheet looks bright at its edge and faint face-on, as a real one does. The FLEX scene was then matched frame by frame against NASA's flight video.

Four phases. First a plan and a map of the data. Then one pilot lab, FLEX, fitted to its tests and reviewed. Then the other four engines, the ranked gallery and the link to the station view. Last, checking: every model against the measurements it can be compared with, every page opened by script, and publishing.

Who did what. The team gathered the NASA data, built the station view, and directed and reviewed the design at each phase. The code for the labs was written with an AI coding assistant (Claude Code) under that direction. ChatGPT is optional and only words the guide's answers.

How it was checked

Each model was run against the NASA measurements it can be compared with. The full report, with the limits of each model, is in docs/VALIDATION.md; node tools/validate.mjs prints the same figures.

Run it or change it

The code sits beside the NASA data in the team repository, in the firelab folder. README.md says how to run it; docs/DEVELOPMENT.md has the notes for adding an experiment, the checks to run and how publishing works.
